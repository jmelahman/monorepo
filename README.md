## Subtrees

Most projects are tracked as [git-subtrees](https://github.com/git/git/blob/master/contrib/subtree/git-subtree.txt).
This allows them to be developed uniformly while leaving operational tasks, such as deployments, independent.

Subtrees and their repositories are listed in [`.config/git-orchard/subtrees`](.config/git-orchard/subtrees) and managed with [git-orchard](git-orchard):

```shell
git orchard status          # ahead/behind each upstream
git orchard pull [prefix…]  # merge upstream changes (squashed)
git orchard push [prefix…]  # publish, fast-forward only
git orchard add <prefix> git@github.com:jmelahman/<name>.git
```

On every push to `master`, [`mirror.yml`](.github/workflows/mirror.yml) runs `git orchard push` for each changed subtree.
Mirror pushes are fast-forward only: if an upstream has commits the monorepo doesn't (e.g. a merged PR), `git orchard pull` it in before the next push.

Releases are tagged in the monorepo as `<prefix>/v<version>`; the mirror job publishes the tag upstream as `v<version>`, which triggers that repository's release workflow.

```shell
git orchard release connections          # tags the next patch version, e.g. connections/v1.2.4, and pushes it
git orchard release connections --minor  # or --major, --suffix rc, or an explicit version like v1.3.0
```

The subtrees' repositories (and the monorepo's own) are configured by [`terraform/github`](terraform/github), which reads the same `subtrees` file.

```shell
cd terraform/github
GITHUB_TOKEN=$(gh auth token) terraform plan
```

To add a subtree:

1. Add it to `subtrees`: `git orchard add`.
2. Give it a description and topics under `overrides` in [`repositories.tf`](terraform/github/repositories.tf), then `terraform apply`.

New Go modules also go in `go.work`.

# Tooling

## Upgrading

### Hooks

```shell
prek update --freeze
```

The [pinsync](pinsync) hook then rewrites every copy of a version pinned in [`.config/pinsync/config.toml`](.config/pinsync/config.toml) on the next `prek run`.
It holds git-orchard's hook rev and prek's CI version at what `uv.lock` locks, so bump those there instead:

```shell
uv lock --upgrade-package git-orchard
uv lock --upgrade-package prek
```

### Golang

```shell
prek run --stage manual go-get
```

This runs `go get -u ./...` from each module's root, in every module whose config includes the `go-get` hook.

## Checks

Linting, formatting and type-checking run as [prek](https://prek.j178.dev) hooks (see `.pre-commit-config.yaml`), with tools pinned by the config or `uv.lock` rather than taken from the host.

```shell
prek install        # once per clone
prek run            # staged files
prek run --all-files
```

The monorepo is a prek [workspace](https://prek.j178.dev/workspace/): each project's own `.pre-commit-config.yaml` runs from that project's directory, and the root config also runs on every file in the tree.
Module-scoped Go checks (`go vet`, `go test`, `golangci-lint`, ...) live in each module's config, since they have to run from a module root.
