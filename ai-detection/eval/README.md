# Benchmarking the detector

`cmd/eval` measures how well this detector separates human from
machine-written text. It has two steps: `score` runs the detector over a
labelled CSV and appends one row per text, and `report` turns those rows into
metrics. Separating them makes a long run resumable and lets several processes
share one sample.

## Data

The default corpus is the test split of [MAGE][mage], which is balanced and
covers ten human domains and 27 language models, including several generation
strategies. It is not committed here; download it once:

```sh
curl -L -o mage_test.csv \
  https://huggingface.co/datasets/yaful/MAGE/resolve/main/test.csv
```

`score` expects a `text,label,src` CSV and follows MAGE's labels: `1` (or
`human`) is human, `0` (or `machine`) is machine. The `src` column is parsed
into a domain, a generation strategy and a model for the per-source tables.

## Running

A representative sample takes a few minutes on a laptop:

```sh
go run ./cmd/eval score --data mage_test.csv --limit 1000 --out scores.csv
go run ./cmd/eval report --scores scores.csv --name "MAGE test"
```

Scoring is CPU-bound on the two Qwen3-0.6B models, so split a larger sample
across processes. Every shard uses the same seeded sample and keeps a disjoint
quarter of it; each writes its own append-only file:

```sh
for i in 0 1 2 3; do
  go run ./cmd/eval score --data mage_test.csv --limit 1000 --seed 1 \
    --shard-index "$i" --shard-count 4 --out "scores-$i.csv" &
done
wait
go run ./cmd/eval report \
  --scores scores-0.csv,scores-1.csv,scores-2.csv,scores-3.csv \
  --name "MAGE test"
```

Rerunning `score` with the same `--out` skips every ID already there, so an
interrupted run resumes instead of starting over. `--json` writes the same
metrics in a machine-readable form, and `--max-words` truncates long texts to
keep a run short.

## What the report means

- **ROC-AUC** is threshold-free: the chance that a random machine text scores
  below a random human one. It is the fairest single number for comparing
  detectors, and its 95% interval comes from a stratified bootstrap.
- **Fixed threshold** applies Binoculars' published Falcon-7B threshold
  (0.9015). It shows what the CLI does today, but that value was not calibrated
  for this model pair.
- **Cross-fitted threshold** calibrates a threshold to a target false-positive
  rate (5% by default) in `k` folds. Each text is judged by a threshold chosen
  without it, so the reported recall is not inflated by tuning on the test set.
  The fold thresholds are printed to show how stable the calibration is.
- **Per-source tables** use the cross-fitted predictions. Machine groups show
  recall (TPR); human groups show the false-positive rate; domains show both.
  Small groups are hidden from the text report but kept in `--json`.

Recall at a fixed false-positive rate is the usual way to report an AI-text
detector: in a deployment, the false alarms on human writing matter more than
raw accuracy on a balanced sample.

## Measured result

A 1,000-text sample (seed 1) of MAGE's test split, scored on 2026-11-04 with
the Qwen3-0.6B pair on CPU and llama.cpp v0.6.0. The full metrics, including
fold thresholds and every group in the tables below, are in
[`mage-test-1000.json`](mage-test-1000.json); the per-text scores, without the
text itself, are in [`mage-test-1000-scores.csv`](mage-test-1000-scores.csv),
so the report can be recomputed in a second:

```sh
go run ./cmd/eval report --scores eval/mage-test-1000-scores.csv
```

| Metric | Value |
| --- | --- |
| ROC-AUC | **0.595** (95% CI 0.559–0.633) |
| recall at 5% FPR, cross-fitted | 24.0% (95% CI 20.4–28.0%) |
| recall at the shipped threshold (0.9015) | 40.0% (95% CI 35.7–44.4%) |
| false-positive rate at 0.9015 | 11.7% (95% CI 9.2–14.8%) |
| accuracy at 0.9015 | 64.7% |

Overall the detector is only slightly better than chance on this benchmark.
The aggregate hides a sharp split by how strong the generating model is
(AUC against every human in the sample, recall at the shipped threshold):

| Machine source | Texts | AUC | Recall at 0.9015 |
| --- | ---: | ---: | ---: |
| GPT-3 7B–65B and GLM130B | 69 | 0.954 | 94.2% |
| text-davinci-002/003 | 86 | 0.871 | 79.1% |
| GPT-3.5-turbo | 46 | 0.774 | 47.8% |
| T0 3B/11B | 28 | 0.610 | 39.3% |
| FLAN-T5 small–XXL | 91 | 0.527 | 24.2% |
| OPT 125M–30B | 128 | 0.340 | 5.5% |
| GPT-J, GPT-NeoX, BLOOM-7B | 40 | 0.141 | 0.0% |

The OPT and GPT-J/NeoX/BLOOM rows are worse than chance: on average those
machine texts score *higher* than human writing, which is the opposite of what
the detector needs. FLAN-T5 is at chance. Two other weaknesses show up in the
breakdown:

- **Continuing a human prompt is hard.** Texts generated by continuation have
  AUC 0.544, against 0.828 for specified and 0.864 for topical generation.
  The human prefix is apparently enough to make the whole passage look human.
- **False positives are concentrated.** At the cross-fitted 5% target,
  HellaSwag (14.8%), ROCStories (19.6%) and TL;DR (13.6%) human text is
  flagged, while six other domains are at zero.

### Interpretation

The 0.6B model pair is the likely bottleneck: Binoculars' published results
use a 7B observer and performer, and a 0.6B model's next-token distribution is
too noisy to separate a weak generator from a person. MAGE is also a hard
corpus by design: more than half of its machine texts come from small models,
continuations, or both. The shipped threshold is not calibrated for this pair
either: it spends an 11.7% false-positive rate, and the cross-fitted 5%
threshold (about 0.842) cuts recall to 24%.

This is a useful negative result, not a verdict on Binoculars. Before calling
the detector calibrated, the next step is to rerun this harness with a larger
pair (the paper's 7B models are the obvious comparison), calibrate the
threshold on a disjoint split, and only then consider a trained classifier on
top of the per-token scores.

Caveats: the sample is 1,000 texts, so per-source rows have wide intervals;
the cross-fitted threshold is still fit within MAGE's test split rather than a
separate calibration set; and scores can shift slightly across llama.cpp
backends.
